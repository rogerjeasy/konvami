# Konvami design

**Source of truth:** the claude.ai Design canvas
https://claude.ai/artifact/LHpzPuTBCcjS5WBXvZsVyG (private). Each artboard shows a phone screen in
light and dark side by side. Build screens exactly as drawn; tokens are in
`packages/design-tokens/src/tokens.ts` (do not copy hex values from the canvas into app code).

**Local copy:** `canvas-2026-10-06/` holds the canvas files as they were on 6 October 2026 (one
`.dc.html` per artboard). Use it when the canvas link cannot be opened; anything changed on the
canvas after that date is not in it.

## Where the app differs from the canvas, and why

| Screen | Difference | Reason |
| --- | --- | --- |
| 2.2, 3.1 | Apple and Google show a "coming soon" notice | They need the Apple Developer and Google OAuth credentials |
| 2.3 | A "Confirm password" field is added | Requested on 2026-10-09 |
| 2.5, 6.7 | Only OpenAI is named, required, with everything it does (conversations, corrections, reports, memories, Tutor answers); no ElevenLabs or Bedrock switches. The consent record is `v2` and stores both as not agreed | Neither is in use, and a switch that changes nothing misleads (decided 2026-10-23). They come back with a new consent version once they are integrated; consent is withdrawn by deleting the account |
| 3.1 | "Email me a sign-in link instead" shows a "coming soon" notice; 3.4 is not built | Cognito can only send sign-in emails through Amazon SES (own sender, production access), which is not set up yet |
| 3.2 | "n tries left before a 5-minute pause" is counted on the device | The service does not say how many tries are left; it keeps its own lockout as well |
| 3.3 | No streak chip and no "persona is waiting" card | That data does not exist yet, and a made-up streak would mislead a real user |
| 3.5–3.7 | A 6-digit reset **code** instead of a reset link; 3.6 has the code field, 3.7 has no "Secure link verified" chip | Cognito resets passwords with a code. The code is checked together with the new password |
| 3.5 | No "Signed up with Apple or Google?" note | Nobody can sign up that way yet |
| 3.7 | No "Not used before" chip | Only the service can know; it refuses a reused password and the screen says so |
| 3.8 | No "We sent a confirmation… Contact support" note | No such email is sent yet and there is no support address |
| 3.8, 2.6 | "this device" instead of "this iPhone" | The same text is used on Android |
| 1.2–1.4, 2.7 | Persona portraits are drawn avatars, not initials on a colored disc | The avatar component of section 4 replaced the placeholder everywhere |
| 4 (all) | Avatars are illustrated in code from a few parts and colors | The painterly, realistic style of decision D17 needs a character artist; the stored look is renderer-neutral so the drawing can be replaced |
| 4.1, 4.5 | Voice works in development and store builds and in the web preview, not in Expo Go | WebRTC is a native module; in Expo Go the screen explains this and offers the form (4.1) or skipping the test (4.5) |
| 4.7 | During onboarding only a partner's name and look can be changed | The rest is changed in Persona Studio (6.6), which opens once the learner is in the app |
| 4.8 | No trial offer on the ready screen | The 7-day trial needs RevenueCat and the store accounts |
| 5 (all) | The tab bar is drawn by the app, not by the system | It uses the design tokens, is the same in the web preview, and becomes a side rail on wide windows |
| 5.1 | No daily plan, due cards or pen-pal notes on Today (spec §14.1) | Those features are not built; Today shows what exists: the partner, the week, the level, what to polish, the exam, recent conversations |
| 5.3 | A conversation lasts at most 10 minutes | The call worker runs on Lambda (15-minute limit) |
| 5.3 | Correction chips show the mistakes of the learner's turn corrected last (at most two), a few seconds after it, under their line; tapping one shows why in a sheet. Only those the checker is sure of and that are not minor are shown; a partner set to not correct gets no checks. A help-sheet switch hides them | A wrong correction is worse than none (spec §16.1); the report checks every mistake again. A turn is checked once its audio is back, so the chip follows the turn (spec §6.4 draws it on the turn as the partner recasts). Design note: `docs/superpowers/specs/2026-10-25-live-coaching-design.md` |
| 5.3 | The plan of the call shows under the lines: the kinds of mistake practised and up to four saved words, each ticked once said; whether a word was used is guessed on the device | The Session Planner is code, not a model (it runs while the call connects); the tick is a nudge, not a score (spec §6.4 "3 of 5 target words used") |
| 5.3 | The five help buttons of spec §6.4 are in one "Help" sheet, beside "Mute microphone" | Five buttons do not fit a 320 pt phone beside the call's controls |
| 5.3 | Help reaches the partner as a note (`learner_help: slower`) that is not a line of the learner; the partner's server-side instructions say what each note means. Translate and Explain are spoken by the partner, not shown as text | The note never appears in the transcript or the report, and the app sends no instructions of its own |
| 5.3 | Captions: the partner's line can be hidden (a switch in the help sheet, kept on the device); no blur-until-tapped, no tap-a-word, no push-to-talk | Hiding the partner's words is the listening practice; the rest builds on it |
| 5.6 | A recorded turn plays, and playing goes on through the turns after it; no word-by-word highlighting, playback speed, search, bookmarks, export or offline copies (spec §6.6) | Hearing a conversation again comes first; the rest builds on the recordings |
| 5.6 | The audio is fetched by the server from the voice provider after each turn (`conversation.item.retrieve`), not recorded on the phone | The phone's WebRTC library cannot record a call without new native code. Not yet tried with a real call (design note 2026-10-22): if no audio comes back, turns simply have no play button |
| 5.6 | Recordings are kept as WAV (about 3 MB per minute of speech), not Opus or AAC, and are not moved to cheaper storage | The Lambda runtime has no audio encoder; for a tester group the difference is cents |
| 5.6 | The learner's lines show the verbatim text when there is one | It is what the report's corrections quote |
| 6.7 | Recordings are kept until the learner turns them off; turning them off deletes the ones kept so far, after a confirmation. Off, the audio is still used for the verbatim pass and deleted right after it | Spec §6.1.2 asks at the right moment; that question belongs to progressive profiling, which is not built. The learner agreed to share their voice with the provider (2.5) |
| 5.10 | The report is read from the conversation's text: no pronunciation notes, pace or pauses, no "play this turn", no level estimate | Those need listening to the recording and the level engine (spec §6.9). The learner's share of the talking is counted in words, not seconds |
| 5.10 | Mistakes can still be missing from a report | The verbatim pass (spec §9.4) is speech recognition too, told to keep mistakes. Measured on synthetic learner speech (2026-10-25, `docs/evals/`): gpt-4o-transcribe keeps 86–89 % of mistakes, wrong verb endings least. There is no "I didn't say that" flag yet |
| 5.10 | A correction the second check could not confirm is shown, marked "Not sure" | Spec §16.1: never as a fact. One the second check calls wrong is not shown at all |
| 5.10 | No "That's wrong" flag on a correction | The review queue (spec §16.1) is not built |
| 5.12 | The Tutor's grounding is one short rule note per kind of mistake the language pack knows (18 for German), not a full grammar reference with retrieval | A curated reference is a content project of its own; the notes cover every topic a report files mistakes under, and the Tutor says when it is not sure (spec §16.1) |
| 5.13 | Eight German scenarios, each played by one of the learner's own partners; no custom scenarios, no rehearsal with a debrief, no regional accents | The scenario library of spec §13.1 starts with the situations a newcomer meets first; rehearsal and debrief are P1 (spec §6.3) |
| 5.4, 5.10 | The goals reached show on 5.4, not in the Session Report | The report reads the transcript; the goals come from the call |
| 5.12 | Questions are typed; no spoken questions outside a call, no mini-lessons or exercises, no `show_card` during a call | Those build on the Tutor (spec §6.8, §8.4) |
| 5.12 | A learner may ask 40 questions a day, in all three ways together | Each is a request to the strong text model |
| 5.3 | While the Tutor answers during a call (a few seconds), the partner is silent | The partner is told to say nothing before a tool call; a "let me think" line is a later refinement |
| 5.10 | A report that keeps failing can be asked for three times in all | Every attempt is two requests to a paid model; storage lets one request, and one worker, through at a time |
| 5.10 | The report and the memories are written by the call worker, not a Step Functions pipeline | Three requests in a row (analysis, second check, memories) need no orchestration yet; a failure of the report does not stop the memories. Cards and the level update will need it (spec §12.2) |
| 5.8 | The level over time is a list of the levels and when each began, under the level card; no trend arrows, no CEFR radar and no fluency trends | The basic level engine moves one overall level (spec §6.9); per-skill trends and fluency need the full engine and recordings (pace, pauses). The level per skill uses the bars of the placement result, not a radar |
| 5.8, 5.10 | The level moves after five conversations, at least four pointing the same way and none the other way, one step at a time; a step down is automatic, with a note on the report | Decided 2026-10-23. Any change, the learner's own included, restarts the count; the learner sets their level in 6.3 Learning at any time |
| 5.10 | The level evidence is the report writer's judgment of grammar, vocabulary and speaking from the transcript; no fluency from audio, frequency bands, help-button counts or frustration and boredom detection | Those are spec §6.9 "full" (P1). Design note: `docs/superpowers/specs/2026-10-23-level-engine-design.md` |
| 5.8 | Mistakes are counted as how often a kind came up per week, not as a rate, and only confirmed ones | A rate needs the words of each kind attempted, which the reports do not have. Unconfirmed corrections are hints (spec §16.1) |
| 5.8 | Eight milestones, without dates and without "Then vs Now" | When a milestone was reached is not stored; Then vs Now needs recordings (spec §7) |
| 5.8 | No weekly report | The weekly report belongs to the Learning Director (spec §6.12) |
| 5.7, 5.10 | A card is made when the learner saves a word or a confirmed correction from a report, one by one or all at once ("Keep what you learned" at the top of the report); nothing is added on its own | The report guesses which words are new, and a deck the learner did not choose is one they stop opening (spec §2.2: ask, don't assume). A correction marked "Not sure" cannot become a card |
| 5.7, 5.11 | A word card shows its forms (article in its gender's colour, plural, verb forms and case, comparison) once the worker has written them, and plays the word with its sentence in the first partner's voice | Forms are written by the stronger text model in the background, sound on first play (spec §6.7 "rich cards"). Design note: `docs/superpowers/specs/2026-10-25-rich-cards-design.md` |
| 5.14, 5.15 | Mastery comes from the uses and mistakes the report's analyst counts per topic; no quizzes, mini-lessons or exercises, no audio on the learner's mistakes | Evidence from conversations comes first (spec §6.8); the counts are not checked a second time like corrections |
| 5.15 | "Practise this in conversation" calls the partner Today suggests, with the topic first in the call's plan | One tap from a weak topic to practising it; the partner can be changed on Talk |
| 5.10 | "Say it better" only on confirmed corrections; the learner says their whole turn with the confirmed corrections put in; right means the corrected words are heard and the wrong ones are not | Drilling a doubtful correction could teach a mistake; a plain word comparison gives the same answer every time |
| 5.10 | The new try is not kept, and attempts do not count towards the grammar map or the cards | The learner's voice is kept only where they chose it (6.7); mastery is evidence from conversations (spec §6.8) |
| 5.11 | Reviewing is tapping, online; no voice review, no review conversation | Voice review and review conversations are phase 2 (spec §18); reviewing offline needs the cards and the scheduler on the device (spec §10.3) |
| 5.11 | The schedule is FSRS with its published default parameters, the same for every learner | Fitting it to a learner needs their review history, which is kept from the first review on |
| 5.11 | A card that was not known comes back once more in the same sitting, ten minutes later at the earliest for the next one | FSRS's relearning step, without its timers |
| 5.1 | "Let's polish this" shows the last report's next steps once there is a report | A report is newer than the placement test; the partners are told the same before a call |
| 6.1 | No subscription or usage on the Profile (spec §14.1) | Those features are not built; the Profile shows what exists |
| 6.2 | The photo is chosen from the library; it cannot be taken with the camera | The app is configured never to open the camera (`app.config.ts`: the Android permission is blocked) |
| 6.3 | No "Ask me again" by voice and no undo of a change (spec §6.1.3, §14.2) | Changing the profile by voice belongs to the full live session; changes are logged on the server but not shown |
| 6.5, 6.6 | Three roles (friend, teacher, exam coach); no role-play, course companion or custom role, no accent choice | Each needs its own instructions and, for role-play, scenarios (spec §6.3); accents depend on the voice provider |
| 6.6 | Voices are listed by the provider's own names, without a description | A sample says more than an adjective would, and none was verified |
| 6.6 | "At the end" corrections are one sentence in the partner's goodbye | The call closes a few seconds after the goodbye (the worker's grace period) |
| 5.3 | A partner asks about what happened since the two last talked, knows what is coming up, and says honestly that they do not recall anything else | They are told at most 20 memories before a call (the newest and the ones marked important); there is no `get_memory` tool to look further during a call (spec §8.4) |
| 6.10 | Memories are short notes with the learner as their unnamed subject ("Has a job interview"), in the explanation language | One text is shown to the learner and given to the partner. "You" would read to the partner as being about themselves |
| 6.10 | Memory is on from the first conversation; the screen has the switch | Spec §6.1.2 asks the first time a memory is created; that question belongs to progressive profiling, which is not built |
| 6.10 | A conversation is read for memories only if it ended while memory was on; one from before memory existed, or one that ended while it was off, is never read, also when its report is asked for later | The learner's choice counts as it was when they talked. It is put on record when the conversation ends, and without that record nothing is read |
| 6.10 | An off-limits topic is a few words the learner types. Partners are told never to bring it up and nothing new about it is written down; a memory that already touches it stays until the learner deletes it | Telling which memories touch a topic needs a model; the learner sees every memory and can delete it |
| 6.10 | "Forget that" cannot be said during a conversation (spec §6.11) | It needs a live tool; the learner forgets a memory on 6.11 |
| 6.10 | What partners know is picked by date, importance and recency, not by similarity to planned topics; nothing is merged or expires | There is no Session Planner and no embedding yet (spec §8.2); a learner keeps at most 300 memories, and consolidation is a nightly job of spec §17.3 |
| 6.10 | A conversation is read for memories once, by the call worker after its report, with the small text model | Memory extraction is a small-model job (spec §17.3 lever 5). On two scripted conversations (2026-10-11) the small model wrote the same memories as the strong one |

## Visual language (v2)

- Graphite and stone surfaces with one deep-teal accent (`primary`: `#0F766E` light,
  `#14B8A6` dark). No purple, indigo, lavender, gradients or glows.
- Lexend SemiBold for titles (28/34), Inter for interface text (16/24 body).
- 54 pt buttons (radius 14), 52 pt fields (radius 12), 44 pt minimum touch target.
- Warnings amber, success green, errors red; learner mistakes use the amber "Let's polish this"
  chip, never red.

## Adapting the phone mockups to other sizes

The canvas draws a 390 × 844 phone. The app keeps that look on every window through
`HeroLayout` and `src/lib/layout.ts`: stacked on phones (hero ≈ 56% of a tall window), actions
pinned at the bottom, content scrolling on short windows or at large text sizes, and hero beside
text on landscape tablets and desktop.
